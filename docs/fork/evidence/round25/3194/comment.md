Fixed the token stage (#3194), in a limited scope, in commit 109e6f47a18cd0540e463089ac9d86656840dac5 on the fix/r25-mcp-invalid-target-retry branch.

**What was wrong.** An authorization server that advertises a resource in its protected-resource metadata may still answer 400 invalid_target to a token request that carries that resource (Semgrep's does). Because the code exchange and every renewal send the resource, the sign-in failed there — the stage after the browser, where the error text could not be acted on.

**What changed (root fix, shared layer).** `tokenRequest` in `internal/mcpauth/mcpauth.go` now posts the form once and, only when the answer is `invalid_target` and the form carried a `resource` parameter, sends it again without that parameter. Everything else about the request goes as it was — the PKCE verifier, the client authentication, the grant — and the saved record keeps the resource the server advertised (only its token stage refused it). No other token-endpoint error is retried, and a request without a resource is never retried, so there is no loop; a server that keeps refusing gets exactly one retry.

**Scope, stated plainly — this is a partial fix.** The rejection at the authorize stage (the browser being sent back with `error=invalid_target` before any token exists) is **not** fixed here: that is browser-side, and this change deliberately leaves it as it is. A real Semgrep server was not exercised; the fix was verified against a fake authorization server that reproduces the behavior.

**Tests.** `internal/mcpauth/renew_resource_test.go` signs in through the real discovery, registration and loopback callback and covers: the code exchange and a renewal both going on without the unaccepted resource, `invalid_grant` not retried, a record without a resource not retried, a persistent refusal bounded at exactly two token requests, the client secret still sent on the retry, and a cancellation during the held retry saving nothing. The fake's token endpoint counts its requests so the bounds are asserted, not assumed.

**RED/GREEN.** On a `git archive` of the base with only the test files added, the new tests fail with real `invalid_target` failures at the exchange and the renewal (exit 1); with the fix they pass (exit 0). `go test -race` passes for `internal/mcpauth/...` and `internal/library`, and for the MCP-targeted `internal/gateway` tests; `gofmt`, `go vet ./...`, Linux/nogui and Windows `go vet` and builds are clean. The full `-race ./internal/gateway` run has three failures and a 10-minute package timeout that the untouched base has too; this change touches only `internal/mcpauth`.
