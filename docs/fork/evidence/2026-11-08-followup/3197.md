The boundary you flagged is real — confirmed from the source, and fixed on a fork branch.

An `event:` name line goes out as soon as it completes. An upstream that dies between the name and its `data:` line therefore leaves the client an event block with a name and no data, closed by the blank line the relay's ending writes. Upstream's own severed-stream test for this shape (`TestPassthroughStreamEndsOnLineEnd`, Messages) constructs exactly the cut and asserts only that the error event begins after a blank line — the empty event before it goes unchallenged. Chat was spared because its SSE has no `event:` lines, which is why the fix this issue landed upstream (`70a40aaa0`, the `[DONE]` ending) never hit this: the orphan needs a named-events route (Responses, Messages, Gemini).

Fix on [`fix/3197-orphan-event`](https://github.com/skygunner/magpie/tree/fix/3197-orphan-event) (head `a5fa3228f996808dc8c2d1628fb89103bafadee4`, on `upstream/main` `c736906b1`): a named event whose data has not come is held back and goes out when the data line does; a name the upstream itself never follows with data is relayed as the upstream sent it (the ended-short path, unchanged); on a sever the held name drops with the half line, so the client's stream ends with whole events only, then the error.

Tests, red on clean `upstream/main` and green at the head: `TestPassthroughResponsesSeveredAfterEventName` (cut right after a name) and `TestPassthroughResponsesSeveredMidData` (cut inside the data line), each asserting no event block without data and the failure named; the whole severed family (`TestPassthroughStreamCutMidLine`, `EndsOnLineEnd`, the Chat severed cases, `TestLoopCutMidLine`) stays green.
